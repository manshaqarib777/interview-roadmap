## 1. One-Line Definition

**IAM is the permission model everything else inherits (L262) — the users (the human identities, L262), the roles (the machine identities, L262), the policies (the permission documents: what action on what resource, L262), and the trust (who may assume a role, L262) — the least-privilege model (L262) that the L172 baseline (L172) runs on in the cloud (L262).**

The one-sentence interview answer: *"IAM is AWS's identity and access management (L262). The identities: users — the humans, with a password or a key (L262); roles — the machine identities, assumed by the Lambda (L266), the ECS tasks (L271), and the humans with the right trust (L262). The permissions: policies — JSON documents that say what action on what resource, e.g. `bedrock:InvokeModel` on the model (L278) (L262). The trust: the role's trust policy — who may assume it (L262). The model's rule is least privilege (L262): every identity gets exactly the permissions it needs — the Lambda (L266) can invoke the model (L278) and nothing else (L262). The AI shape: the API Gateway (L267) authenticates and invokes the Lambda (L266); the Lambda's role (L262) calls Bedrock (L278), reads the S3 (L265), and writes the logs (L274) — each with the least privilege (L262). The demo uses the root key; the architect uses IAM (L262)."*

The badge rules (the policies, L262) are the printed access lists: what each badge may open (L262). And the trust (L262) is the guard's instructions: who may check out which service badge (L262). ## 4. How It Works — The Model, Part by Part

- **The users (L262).** The human identities — with a password for the console or a key for the API (L262). The humans don't get keys in production (L262); the machines do (L262).
- **The roles (L262).** The machine identities — assumed by the Lambda (L266), the ECS tasks (L271), the EC2 instances (L264) (L262). The role carries the permissions, not the caller (L262).
- **The policies (L262).** The permission documents — JSON: `Effect`, `Action`, `Resource` (L262). The policy says what action on what resource — `bedrock:InvokeModel` on the model (L278), `s3:GetObject` on the bucket (L265) (L262).
- **The trust (L262).** The role's trust policy — who may assume it (L262). The Lambda (L266) may assume its role; nothing else may (L262).
- **The least privilege (L262).** The rule: every identity gets exactly the permissions it needs (L262) — nothing more (L262).

> [!NOTE]
> **The role is the production identity (L262).** The users are for the humans (L262); the roles are for the machines (L262). The production shape has no long-lived keys (L262): the Lambda (L266) assumes a role (L262), the ECS task (L271) assumes a role (L262), and the EC2 instance (L264) assumes a role (L262) — the credentials are temporary (L262) and scoped (L262). The Secrets Manager (L275) holds the keys that can't be roles (L275).

## 9. Best Practices

- **Use roles, not keys** (L262) — the Lambda (L266), the ECS tasks (L271), the EC2 (L264).
- **Scope every policy** (L262) — the action and the resource (L262).
- **Write the trust narrowly** (L262) — who may assume the role (L262).
- **Review the policies** (L262) — the audit's evidence (L322).
- **Keep the exception keys in Secrets Manager** (L275) — rotated and scoped (L275).

## 10. Interview Questions

**Q: Walk me through IAM.**
> A: The permission model (L262). The identities: users — the humans; roles — the machines (L262). The policies: JSON documents — what action on what resource (L262). The trust: who may assume a role (L262). And the rule: least privilege (L262).

**Q: Why roles and not keys?**
> A: Because the keys are long-lived and unscoped (L262). The role is temporary and scoped (L262): the Lambda (L266) assumes its role, gets the credentials for the session, and the permissions are exactly the policy's (L262). **Q: How does the Lambda get its permissions?**
> A: Through its execution role (L262). The Lambda (L266) is configured with an IAM role (L262); the role's policy says what the Lambda may do — invoke the model (L278), read the S3 (L265), write the logs (L274) — and the trust policy says the Lambda service may assume it (L262).

**Q: What's least privilege?**
> A: Every identity gets exactly the permissions it needs — nothing more (L262). The Lambda (L266) may call the model (L278) and nothing else (L262); the reader role may read the bucket (L265) and nothing else (L262). Least privilege is the L172 baseline, IAM-shaped (L262).

## 13. Code Example — The Lambda's Role

```js
// The least-privilege role for a Lambda (L262, L266).
// THE ROLE (L262) — the machine identity the Lambda assumes (L266).
const lambdaRole = {
  AssumeRolePolicyDocument: {
    Statement: [{
      Effect: 'Allow',
      Principal: { Service: 'lambda.amazonaws.com' },   // the trust (L262)
      Action: 'sts:AssumeRole',
    }],
  },
};

// THE POLICY (L262) — what action on what resource (L262).
const permissions = {
  Statement: [
    // The model access (L278) — nothing else.
    { Effect: 'Allow', Action: 'bedrock:InvokeModel',
      Resource: 'arn:aws:bedrock:us-east-1::foundation-model/*' },
    // The data access (L265) — the one bucket, the one prefix.
    { Effect: 'Allow', Action: 's3:GetObject',
      Resource: 'arn:aws:s3:::docs/*' },
    // The logs (L274) — the write, not the delete.
    { Effect: 'Allow', Action: 'logs:CreateLogStream',
      Resource: '*' },
  ],
};

// The result: the Lambda (L266) may invoke the model (L278),
// read the docs (L265), and write the logs (L274) — nothing else (L262).
```

```text
What the reader must SEE — the least privilege, declared:

  lambda.amazonaws.com → the trust — who may assume the role (L262)
  bedrock:InvokeModel  → the model access — nothing else (L278)
  s3:GetObject         → the data access — one bucket (L265)
  logs:CreateLogStream → the logs — the write, not the delete (L274)

  The role is the boundary; the policy is the scope (L262).
```
